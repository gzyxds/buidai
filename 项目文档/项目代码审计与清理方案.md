## 一、P0 — 性能与正确性问题（建议优先处理）

### 1.1 `AppNavigation.vue` 整个滚动监听是死代码

**定位**：`components/AppNavigation.vue:427-432`、`437-442`、`627`

```ts
// :430 恒返回 false
const isTransparent = computed(() => {
  return false
})
```

`isTransparent` 永远为 `false`，导致：

- `headerClasses:437-442` 中的 `isScrolled.value` 分支**永不执行**
- `navigationMenuUi:447-456` 中 4 处三元表达式永远走 else 分支
- `isScrolled = useScrollThreshold(SCROLL.THRESHOLD):627` 及其注册的 scroll 监听**完全无消费者**

**影响**：每个页面都白挂一个 scroll 监听 + rAF 循环；`navigationMenuUi` computed 每次求值都构造 4 个永不命中的死字符串。

**改法**：删除 `isTransparent` / `isScrolled` / `useScrollThreshold` 引入，`headerClasses` 直接返回常量，`navigationMenuUi` 去掉 4 处三元。

**影响范围**：仅导航栏样式类计算逻辑，视觉输出**完全不变**（因为死分支本就不执行）。零风险。

### 1.2 `FallingText.vue` 双重物理循环，步进速度翻倍

**定位**：`components/FallingText.vue:296-321`

```ts
Runner.create()
Runner.run(runner, engine)      // :298 —— Runner 内部已用 rAF 驱动 Engine.update
...
const updateLoop = () => {
  wordBodies.forEach(...)       // :308 每帧直写 style.left/top/transform
  MatterLib.Engine.update(engine)  // :318 手动再步进一次（重复）
  animationFrameId = requestAnimationFrame(updateLoop)  // :319
}
updateLoop()  // :320
```

**问题**：

1. `Runner.run` 已包含 `Engine.update` 循环，`updateLoop` 又调一次 → **物理步进速率是设计值的 2 倍**
2. `:308-313` 每个物理体每帧直写 `style.left/top/transform` → 强制 layout，破坏合成层
3. `Runner.run` 与 `updateLoop` 是两个独立的 rAF 循环，帧序不同步

**改法**：保留 `updateLoop` 的 DOM 同步，移除 `Runner.run(runner, engine)`（或反之），只保留一个 rAF 循环；DOM 写入合并为单次 `transform`（去掉 `left/top`，用 `translate3d` 一次性表达）。

**影响范围**：首页 Hero 区 + FeatureSteps 区的文字下落动画。**视觉表现会变**（速度回归设计值），需确认当前 2 倍速度是否为有意的视觉调优。若无明确意图，按此改。

### 1.3 `useScrollProgress` 强制 reflow + layout 触发

**定位**：`composables/useScroll.ts:36-53`

```ts
const winScroll = document.body.scrollTop || document.documentElement.scrollTop  // :43 读 body
const height = document.documentElement.scrollHeight - document.documentElement.clientHeight  // :44 读布局
progress.value = ...
```

**问题**：

1. 同一 rAF 内连续读 `scrollTop` → `scrollHeight` → `clientHeight`，每次读都强制同步 layout
2. `document.body.scrollTop` 在 Standards 模式下恒为 0，白读一次
3. 每帧计算 `scrollHeight - clientHeight`，文档高度变化时（如图片加载）需重算却从不缓存
4. 返回**百分比**（0-100 的浮点），消费方若绑到 `width` 上则每帧触发 layout

**改法**：改读 `document.documentElement.scrollTop`；缓存 `scrollHeight - clientHeight`（用 `ResizeObserver` 失效）；返回值改为 `0-1` 的 ref，由消费方决定渲染方式；消费侧改用 `transform: scaleX()`。

**影响范围**：`pages/blog/[...slug].vue` 的阅读进度条。视觉可保持等价（`scaleX(progress)` ≡ `width: progress%`）。零风险。

### 1.4 `HeroSection.vue` 跑马灯 SSR/CSR 数据不一致 + resize 重建

**定位**：`components/landing/HeroSection.vue:288`、`340-348`、`363-372`

**问题**：

1. `marqueeImageGroups` 在 SSR 用 `initMarqueeGroups()`（固定顺序）渲染 16 张图，`:340` 在 `onMounted` 立刻 `generateMarqueeGroups()` 重新 shuffle → **hydration 不匹配 + 16 张图重复请求**
2. `:363-372` resize 虽做了 rAF 节流，但每次触发都调 `generateMarqueeGroups()` 重排数组并**重建 4 个 `UMarquee` 组件**（`:201-275` 共 16+ 张图）

**改法**：

1. 初始顺序与客户端保持一致（不做 shuffle，或 shuffle 后用 `onNuxtReady`），消除 hydration mismatch
2. resize 只需判断移动端/桌面端断点，用 `useMediaQuery('(max-width: 768px)')` 替代 resize 监听，断点不变时不重建

**影响范围**：首页 Hero 跑马灯。修复 hydration 报错与重复图片请求。

### 1.7 `app.vue` 的 `page-key` 用 `fullPath` 导致 query 变化时整页重建

**定位**：`app.vue:5`

```vue
<NuxtPage :page-key="(route) => route.fullPath" />
```

注释说明是为了处理 `/product/a → /product/b`。但 `fullPath` **包含 query**，任何查询参数变化都会销毁重建整页组件（如 `/plugin?category=video` 切换筛选条件 → 全量重挂载，丢失所有组件状态）。

**改法**：改用 `route.path`（仅路径变化才重建），恰好满足原注释意图（`/product/a → /product/b` 是 path 变化），同时避免 query 变化的重挂载。

**影响范围**：所有带 query 的页面（`/plugin` 筛选）。**改善体验**（筛选不再重置状态）。

---

### 1.8 `ProductShowcase.vue` 全局 keydown 监听未限定作用域

**定位**：`components/landing/ProductShowcase.vue:557`

```ts
window.addEventListener('keydown', handleKeydown)
```

在任意输入框/文本域按左右箭头都会切换轮播（甚至影响页面内其他组件）。

**改法**：改为容器元素上的 `@keydown`，或回调内先检查 `e.target` 是否为可编辑元素。

**影响范围**：首页轮播交互，行为更符合预期。

## 附：核实过程说明
